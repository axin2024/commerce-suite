# 企业采购 1.0 验收记录

运行环境为 Windows 64 位、PHP 8.2.30、MySQL 8.4.13。集成测试使用隔离的 InnoDB 库，网页测试通过本机 PHP HTTP 服务登录各角色。支付、送货和银行流水均为合成数据。

| 场景 | 操作及读回 |
| --- | --- |
| A1、A2 | 两门店共用一个法人，采购员仅能查看授权门店。收货员保存采购详情链接，撤销授权后再次请求返回 404。 |
| A3、A4 | 99 件每件 10 元，100 件每件 9 元；同优先级在 100 件处重叠时，网页标出相交区间。 |
| A5、A6 | 两个商家分别提交 900 元与含运费 1015 元的密封报价。迟到版本可查；重复授标返回原订单。 |
| A7、A8 | 两个独立数据库连接争用 1000 元预算，每份申请 900 元，成功一份，余 100 元。授信不足时新预留回滚。 |
| A9、A10 | 同一行采购 100 件，先收 60 件再收 40 件。第二次写入成功后中断工作进程，重连重送仍只有一份回执。多收 1 件被拒。 |
| A11、A12 | 应收 900 元分两笔到账，600 元与 300 元分别分摊后，该单信用占用归零。再次导入原文件，流水编号、核销金额和信用分录均相同。 |
| A13 | 网页先收 60 件后关账，再从该回执退 10 件。读回三个实际 CSV 的关联字段，原账单再次下载时内容一致。 |
| A14 | 1 万份独立 SKU 协议，100 名授权采购员、100 个独立 PHP 进程同时报价并申请。每人先预热 4 次，100 个计时样本报价 P95 为 7.862 ms，提交窗口 527.402 ms。10 单占满 9000 元授信，90 单因额度不足拒绝；100 个进程全部返回。 |

报价计时覆盖 PHP 服务方法和 MySQL 往返。原始报告保留每名采购员的起跑偏移、报价耗时、总耗时和结果。[容量数据](procurement-load.json)

## 跨月导出样本

网页测试提交的原始需求为两行同 SKU，分别 60 和 40 件，免运费。商家发布 100 至 200 件的 900 分单价；买家全部授标。收货单号 `DOCK-WEB` 首批实收 60 件、破损 0 件，退货单号 `RETURN-WEB` 退回 10 件。

| 下载件 | 账期 | 授标 / 订单 / 行 / 收货回执 | 数量 | 金额（分） |

| 冻结账单 #1，账单行 #1 | 2026-11 | 1 / 1 / 1 / 1 | 60 | 54000 |
| 贷项行 #2 | 2026-12 | 1 / 1 / 1 / 1 | 10 | -9000 |

## 复验

使用空的 `*_test` 数据库，按 [README](../README.md) 设置连接和 `APP_DEMO=1`。迁移后运行 `php tests/integration.php`。网页测试使用另一个已迁移、刚执行过 `seed` 的库；启动服务后运行 `python tests/web_smoke.py http://127.0.0.1:8080`。容量测试独占第三个库，运行 `php tests/capacity.php procurement`，MySQL 须允许至少 101 个连接。

升级演练从 v0.3.0 的数据库备份还原。迁移前后逐行比较了 32 张零售主单、39 张商户单、21 笔付款、21 笔退款、38 笔分录和 4 个结算批次。审查范围包含业务编号、状态、归属和相关金额。预检的零售与采购归属冲突均为零。
